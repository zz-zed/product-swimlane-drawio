# Regression and review evidence

## Scope and compatibility

Version 0.5.1 changes release checks and developer evidence tooling, and fixes
one strict-validation false positive: phase Z-order is checked among siblings,
not across unrelated parents in Draw.io's depth-first serialization. Actual
unsafe layering, visibility and interaction still fail. Routing, semantic
hashes and patch permissions are unchanged. Container ancestors participate in
the order check so reparented connectors cannot pass behind the pool or layer.
Unknown cells now anchor sibling order during phase normalization; unresolved
layering conflicts refuse output. `compare` also detects sibling-order and
full unmanaged-subtree differences, adding optional evidence fields only when
applicable. This intentionally rejects previously missed differences while
keeping clean receipt shapes unchanged.
Generated XML changes only
the `data-tool-version` stamp from 0.5.0 to 0.5.1. The CLI remains a single-file,
standard-library tool. New review fields below are a **draft sidecar contract**,
not accepted build/patch fields or a new CLI command.

## Release inventory

Run `python3 -B tools/release_check.py` in a source checkout. It checks Git's
tracked files plus nonignored candidates against `release-files.json` for the
whole repository and the explicit five-file Skill inventory. Extra sibling
Skills, private payloads, and generated diagrams outside the Skill also fail
the outer allowlist; adding an intentional public file requires a reviewed
manifest update. Ignored local caches are not publication candidates; tracked caches,
unknown binaries, missing files and invalid UTF-8 text fail. Git failures do not
silently switch to a weaker scanner.

For an unpacked distribution, use `python3 -B tools/release_check.py --root
<export-root> --export`. Every release file is checked, including caches. This
must run against the actual staged/exported contents, not just a clean source
directory. Both plugin manifests continue to select the same Skill directory.
The repository test/tooling files are not added to the installed Skill.

## Frozen CLI baseline

`tests/fixtures/cli-contract-v1.json` was captured from the 0.5.0 runtime before
the version stamp changed. `tools/regression_baseline.py` prints a candidate
snapshot; it never rewrites the baseline. Review intentional differences before
changing the fixture. The tests check command exit codes and fingerprints of
the complete JSON result, stderr, generated bytes, ordered diagnostics,
inspect, semantic hashes, patch/compare receipts and rejected output state.

Normalization is limited to the temporary directory, the tool-version stamp,
and file SHA-256 values affected by that stamp. No geometry, style, waypoint,
semantic hash, diagnostic or receipt field is discarded. Receipt stamps
are normalized only when they are valid baseline versions and
match the actual corresponding input/output artifact. Null, malformed or
incorrect stamps stay visible, and an independent mutation test detects a
broken `input_tool_version`. Repeated same-version
builds also compare exact XML bytes without normalization. Reversing only the
unordered node/edge arrays must preserve per-cell attributes/geometry and
validation, not sibling paint order; the enhanced compare reports a real
paint-order change. Lane order and main-path order are not permuted.

The small synthetic corpus is deliberately not an editor golden corpus:

| Case | Expected result | Coverage |
|---|---|---|
| linear-v1/v2/v3 | strict pass, patch and compare pass | legacy compatibility, hashes, receipts, deterministic generation |
| decision-retry-phases | strict pass | same-lane decision, forward/retry, independent phase rail |
| request-response-retry | strict refusal, `routing/edge-conflict` | automatic multi-lane conflict retained as a known routing limitation |
| explicit-port-conflict | build refusal, occupied-port diagnostic | explicit locks must not be overridden or waived |

Failure cases are assertions of the precise refusal, not skipped/xfail tests.
They are not delivery-quality diagrams. More three-lane fan-out, dense labels,
high-pressure and editor-operation combinations remain future corpus work.

## Real editor corpus

Keep original editor files and screenshots in a local evidence directory, not
in Git history. A machine-generated or XML-mutated sample must never be called
an editor round trip. Minimum records identify:

- Editor product/version, OS, operation, timestamp and reviewer.
- Original generated file hash and editor-saved file hash.
- Separate open/save, node move, resize, style, edge redraw/reconnect, phases,
  and unknown-cell cases, with `completed`, `failed`, or `not_run` per operation.
- Inspect/strict/patch/compare outcomes for the exact saved file, including
  unknown attributes, cells, style, geometry, endpoints, waypoints and Z-order.
- Preview export, model visual review and human review as independent states.

An absent editor-saved file means the editor gate is **not completed**. Export
through the editor's CLI is renderer/codec evidence, not proof of interactive
move/reconnect behavior. Public extraction requires separate approval and must
retain only neutral assertions, not a renamed complete XML document.

## Bounded performance evidence

Run `python3 -B tools/performance_probe.py --sizes 60 120 250 500 --timeout 15
--repeats 2`. Each sample is an isolated, timeout-bounded child process. JSONL
records include Python/OS/architecture, fixture hash, tool version, repeated
sample index, elapsed build/validation time, peak worker RSS, and function
profiles. All sizes use the same labeled linear topology family; this is not a
complex-routing capacity claim or a speed SLA. Compare identical sizes and
hashes under the same environment/profiler; cProfile overhead is included.

Routing and label-placement profile costs are inclusive and may overlap.
Label/node, label/edge and label/label checks also have a separate timed replay
on the same generated geometry. Its preparation is excluded; its time is **not**
a measured slice of `validation_seconds`. Timeout/error records are not quality
passes, and unavailable memory/timing values are null, never zero. Do not mix
successful smaller cases and timed-out larger cases into one mean.
Input bounds are 2–5000 edges, 1–10 repeats, and a finite per-sample timeout of
at most 60 seconds. On platforms without `getrusage`, RSS is `not_available`/null.

## Draft arrowhead-clearance rule (not enabled)

Candidate code: `routing/arrowhead-clearance`, severity `warning`. Measure the
final effective segment from its last bend to the rendered target attachment,
in diagram pixels. Evidence must bind edge/target IDs, final segment endpoints,
measured length, threshold and threshold version, arrow style/size, stroke,
target shape/perimeter, view scale and renderer version. A candidate 20 px
threshold is not calibrated and must not become a default yet. The existing
16 px internal-segment check is a separate rule.

Calibrate process and diamond targets, different arrow sizes/styles, zoom,
short terminal segments and explicit manual waypoints. Unknown rendering
geometry produces `not_available`, not a pass. Do not move locked ports or
waypoints to satisfy this rule. Enabling it requires a documented rule version
and compatibility note because existing strict calls also reject warnings.

## Draft visual issue sidecar (not a runtime API)

An evidence record contains `contract_version`, input/output SHA-256,
tool/schema versions, editor/exporter versions, font inventory (or explicit
unavailability), preview hash/path, reviewer identity/type, time and independent
`strict_validation`, `preview_export`, `model_visual_review`, `human_review`
states (`passed`, `failed`, `not_run`, `not_available`). Exporting a preview
does not imply it was reviewed.

Each issue contains a namespaced code, severity, bound semantic ID and kind,
preview hash, screenshot region `{x,y,width,height}` in image pixels, observed
evidence, suggested action and `binding_status`. Validate IDs against the exact
output hash; unresolved bindings cannot authorize a repair. An observation is
not a deterministic diagnostic or a business-fact verdict.

Future repairs require a confirmed whitelist of layout-only intent, frozen
manual geometry, separate candidate output, at most two rounds, strict and
compare validation, and a last-good artifact. No automatic repair or new
semantic/visual review claim is implemented in 0.5.1.
